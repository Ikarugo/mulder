The outcome framework that mulder declined

A single architecture, submitted as a numbered series from 0.2 to 8.4, that would have rebuilt mulder around typed tool outcomes and verifiable claims. Every part of it was closed. This is what it proposed, and what the objection actually was.

The shape: a trust substrate everything else stands on

The series is not a bag of features. It is one tower. Layer 0 changes what a tool returns; layer 1 changes what a finding is; every layer above assumes both. That dependency is the whole story of why it was closed as a unit.

What each layer added

0.2–0.3

Typed tool outcomes

Every tool response carries a ToolOutcome: a ten-value status (SUCCESS_EMPTY, PARTIAL, SAMPLED, UNSUPPORTED_VERSION, NOT_RUN…) plus coverage metadata — rows examined against rows total, truncation and sampling reasons, parser version. The legacy success/error field stays for compatibility.

models.py · contracts.py

1.1–1.4

Claims instead of prose findings

A finding decomposes into AtomicClaims, each pinned to an EvidenceAnchor with exact offsets. verify_claim checks them deterministically rather than trusting narration. An independence gate stops one source being counted twice, and a coverage register turns “we found nothing” into a ScopedNegativeVerdict — nothing found within what was actually examined.

verification/claims.py · verification/policy.py

2.1–2.4

Tamper-evident case history

Findings become event-sourced revisions. The audit log becomes a hash chain from a genesis digest, each entry committing to its predecessor. The case seals into a portable manifest that verifies offline, optionally signed by the examiner with Ed25519.

receipt.py (2,324 lines) · case_signing.py

3.1–3.4

Boundaries around hostile input

Evidence travels in an EvidenceEnvelope carrying a trust label, provenance, truncation metadata and markup-detection flags — the assumption being that evidence text is attacker-authored. A provider policy decides and records every outbound field before an adapter sees it, with a zero-egress preflight for air-gapped work. A command policy declares network class and path access per invocation; privileged mounting moves behind a separate helper with its own identity.

security/ · execution/ · orchestrator/capabilities.py

4.1–4.3

Measurable detection quality

A benchmark manifest, result schema, scorer and ablation matrix — so a change to detection logic can be scored rather than argued.

benchmark/

5.1–5.4

Human review before publication

A transport-neutral read-only model over the case, a local browser console, recorded analyst decisions and approvals, and publication states gating rendered output.

review/ (model.py alone is 1,415 lines)

6.1–6.3

The case as a graph

Entities, events and provenance projected into SQLite over verified claims, with bounded queries, alias-collision handling and explicit hypotheses with discriminators.

graph.py · graph_query.py · reasoning.py

7.1–7.5

Domain packs and immutable intake

A versioned pack contract bundling classifiers, tool bindings, hunts, gates, fixtures and benchmark expectations — instantiated for anti-forensics/clock analysis, a sealed Linux live collector, and EVTX/Kubernetes/cloud pilots. KAPE and Velociraptor collections arrive content-addressed and immutable; runs gain durable handles, phase checkpoints and cancellation.

packs/ · linux_live/ · adapters/intake.py · run_state.py

8.1–8.4

Third-party extension

Plugin discovery with supply-chain metadata, and reviewed import/export connectors.

plugin_packs.py · supply_chain.py · connectors/

Five further branches (R0–2, R3, R4, R5–6, R7–8) were remediation of the framework itself — closing enforcement gaps and race conditions in the layers above, not defects in mulder as it exists.

What actually changes

The objection is easier to see as a hop count. Today a tool result reaches a finding in three steps; the proposal routes it through seven, and the four added ones are the contract nothing yet enforces.

Why it was declined

The underlying concern about failures appearing as empty evidence is valid, but I don’t want to adopt this universal outcome framework in its current form. It introduces a second status taxonomy and an ongoing classification burden across roughly 150 tools, while no current MCP schema or orchestrator consumer enforces or uses the contract. maintainer review on #32 — the only substantive review in the series

Two taxonomies

ToolOutcomeStatus does not replace the existing success/error field, it sits beside it. Two answers to “did this work?”, free to disagree.

No consumer

Nothing reads the contract. The fields would be written by every tool and enforced by nothing, so drift is invisible until it matters.

Partial rollout is worse

A coverage register filled in by some tools and not others yields negative conclusions that are contradictory and falsely precise — the opposite of the goal.

The objection is architectural, not about correctness. The same review closed with an explicit invitation:

Focused fixes for specific tools that currently swallow failures or lose partial-result information would be welcome.

The remaining 31 closures carried identical boilerplate — do not revise the branch in place; resubmit narrowly scoped, based on current main, without the framework.

What was worth keeping

Two real fixes were buried in the framework code

#39 — audit digest collisions. Under 514 lines of hash-chain machinery, hash_output() committed only a length, a key set or a 256-character prefix for large payloads, so different tool outputs produced the same audit digest. Fine as a cache fingerprint, unusable as an audit record. The maintainer found and fixed this independently.

#42 — the executive summary. Under an evidence-envelope refactor sat a fix for HTML report rendering: the summary block was being escaped into visible markup, and the finding titles inside it were interpolated unescaped. Recovered as a five-line change.

The other 34 branches were framework-only. The four most promising were checked individually — the runtime-remediation commits all bind the framework’s own objects, and the intake branch’s 354 lines in the orchestrator are checkpoint plumbing.

The valid part of the concern — a failed tool reported as a clean scan — was then addressed the way the maintainer asked: one narrow, independently verifiable fix per tool, each proven against the real pinned binary rather than the framework’s abstractions.

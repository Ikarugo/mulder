## Analysis of Misses and Errors

### Where the budget went

The 300 calls (307 in the audit log) went to `search` (60), `open_case` (21), `get_raw_output` (18), `get_investigation_summary` (17) and 12 `submit_finding`s, against run 1's 222 with 73 searches. The extraction batch indexed the same source set as run 1 minus `tsk.fsstat` (so no RM2 label) and read `optical.listing` without reporting it. The one new thing in this run's evidence handling is a direct `query_registry_value` walk of `ControlSet001\Enum\USBSTOR` down to both serial subkeys, which is where items 3, 4 and 12 get their content; nothing else in the report is deeper than run 1.

### The disc read and lost (items 5, 16; FP 1)

Run 1 read the disc and built the wrong chain from it (CD as source). This run's rm3 agent read the same listing, noted in the log that "session 0" was created on March 24 and the deleted files carry December–January dates, and then used those dates to give the masquerading finding a January window while never submitting a finding about the disc. The result is two MISSED items where run 1 had two PARTIALs, and a false positive that run 1 did not make: the disc's file mtimes are narrated as a January "Initial Discovery and Planning" phase with cloud access, before the OS existed. The correct in-run observation ("Optical media (session 0) created on March 24, 2015") never reached the report either.

### RM2 never named (items 4, 7, 15)

`detect_masquerading` returned 17 lines on rm2 and the finding is built from them, but the report puts the files in "$OrphanFiles/ directory" on "the system" and never says RM2, FAT32 or "IAMAN $_@" (`tsk.fsstat` was not run). The second USBSTOR serial with its 13:58:33Z LastWrite is RM2's first connection to the second and is not attached to any image. Item 7 loses its FOUND to the missing device and the January date; item 4 trades run 1's label for a serial; item 15 keeps the deletion and loses run 1's device and window.

### The counter-analysis that changed nothing (items 8, 19; FP 2)

The 23:06 counter-evidence pass returned three results that should have altered the report: Eraser in the MFT under Program Files (item 8), "1,797 unique email addresses extracted" (item 19), and the Tor IP absent from `bulk.domain` (FP 2). None was acted on: no Eraser finding was submitted, no address was reported, and the Tor finding went to the IOC table and containment at HIGH.

### Registry basics (items 2, 20)

Four `query_registry_value` calls, all `USBSTOR`. "Windows 7 Professional" is asserted with no query and no log hit; `TimeZoneInformation` was not read and no timestamp in the report is placed in a zone. The four-hour FAT32 offset that run 1 printed and missed is not printed this time.

### Search history and cloud dates (items 9, 10, 11)

`bulk.url_searches` (155 lines) is used for the first time in a MiniMax run and yields five exact Q16 terms, all on the leakage side; none of the anti-forensics terms, which sit in the same 155 lines. Drive and iCloud are both present with executables, paths and browsing, and both are dated March 22, the OS install date, instead of March 23; the same March 22 is given for the searches. Three items gain or hold PARTIAL on content and are held there by one wrong date.
